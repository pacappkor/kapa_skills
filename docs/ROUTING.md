# 진입점·라우팅·폴더 구조 설계

이 문서는 「감정평가 실무기준」 컬렉션을 에이전트가 어떻게 들어오고 찾고 적용하도록 할지 검토한 결과다.

## 1. 문제

감정평가 실무기준에는 분류 축이 여럿 있다. 물건별([600]), 목적별([700]), 일반 평가와 보상평가([800]) 등이다.
처음 설계는 이 축을 그대로 폴더(common/object/purpose/compensation)와 진입 질문(평가 체계 → 목적 → 물건)으로 썼다.
그러나 축은 원문의 편집 단위일 뿐, 에이전트에게 가장 좋은 진입점이라는 보장은 없다.
검토한 질문은 세 가지다.

1. 에이전트는 어떤 단서로 들어오는가?
2. 관련 조항을 어떻게 찾는가?
3. 여러 규정이 걸릴 때 무엇을 우선하는가?

## 2. 근거: @skills (arXiv:2608.12610)

| 논문의 관찰·원칙 | 설계에 주는 함의 |
|---|---|
| 설치된 스킬의 description 은 프롬프트에 상주하며 신뢰할 수 있는 트리거 슬롯(100개 미만)을 다툰다. 상주는 자동 트리거에만 필요하다 | 상주는 입구 하나로 충분하다. 나머지는 경로로 읽는다 |
| 경로가 주소다. 디렉터리는 메뉴다. leaf rule 을 따른다 | 폴더는 "한 번에 보여 줄 메뉴"의 단위다. 메뉴가 짧고 균질해야 한다 |
| 명시적 참조는 여러 스킬을 결정적으로 함께 불러온다. 확률적 매칭은 스킬 수가 늘수록 실패가 누적된다 | 라우터는 "읽을 스킬 목록"을 명시적으로 출력해야 한다. 모델의 연상에 맡기지 않는다 |
| 파일 트리는 주소를 붙일 뿐 찾아 주지 않는다. 찾기(검색·색인)는 별도 층의 일이다 | 찾기용 색인과 원문 검색을 따로 둔다 |
| 검색 기반 트리거는 상주 없이 발견을 돕지만 활성화가 다시 확률적이 된다. 그래서 보완재다 | 임베딩 검색 대신, 결정적인 생성 색인과 grep 을 쓴다 |
| description 은 조용해야 한다(트리거 문구 경쟁 금지) | description 은 "실무기준 [조항] 무엇의 기준" 형식의 사실 한 줄로 쓴다 |
| 스킬은 읽으면 바로 쓸 수 있어야 한다. 참고 파일은 필요할 때만 연다 | SKILL.md(요약·확인사항·연결)와 source.md(원문)를 나눈다 |

## 3. 검토한 진입 방식

| 방식 | 장점 | 한계 | 채택 |
|---|---|---|---|
| A. 원문 축 분류 (평가 체계 → 목적 → 물건) | 원문 구조와 같다. 사람에게 익숙하다 | 의뢰는 여러 축의 곱이다(담보 × 아파트). 질의·검토·수임 판단은 축과 맞지 않는다. 같은 개념이 여러 장에 흩어져 있다(기준시점: [100]·[300]·[730]·[810]). 충돌 해결 규칙을 주지 않는다 | 조회표로 강등 (facets.md) |
| B. 작업 유형 (평가 수행·조항 질의·평가서 검토·수임 판단·개정 확인) | 에이전트가 받는 요청의 첫 단서다. 유형마다 필요한 절차가 다르다 | 유형 판별 뒤에도 규정 선택은 따로 해야 한다 | **입구** |
| C. 절차 단계 ([400-1] 7단계) | 원문이 정한 작업 순서다. 단계마다 필요한 조항만 읽으면 문맥이 작다 | 단독으로는 어떤 특칙이 걸리는지 모른다 | 평가 수행·검토의 **읽기 순서** |
| D. 적용 규정 결정 (적용·준용 조항으로 만든 우선순위 스택) | 원문 스스로 정한 우선순위다. 축은 이 결정의 입력 사실(F1~F6)이 된다 | 사실 확정이 먼저 필요하다 | 평가 수행의 **핵심** |
| E. 용어·조항 색인 + 원문 grep | 결정적이다. 질문 낱말에서 바로 조항으로 간다. 개념이 흩어져 있어도 모두 나온다 | 동의어·활용형에 약하다 | **찾기** |
| F. 인용 그래프 | "준용"·"따른다"로 이어진 조항을 빠짐없이 모은다 | 출발 조항이 필요하다 | 찾기의 마지막 단계 (자동 생성 "참조 관계") |
| G. 임베딩 검색 | 동의어에 강하다 | 확률적이고 인프라가 필요하다. 같은 질문에 다른 답이 나올 수 있다 | 미채택 (논문도 보완재로 봄) |

결론:
- **입구**: 작업 유형(B)
- **평가 수행**: 결정 사실 → 우선순위 스택(D) → 절차 단계별 읽기(C)
- **찾기**: 색인·grep·인용 그래프(E+F)
- 원문 축(A)은 결정 사실을 스킬로 바꾸는 조회표로만 남긴다.

## 4. 폴더 구조

원문 축 대신 **역할 층**으로 나눴다. 평가 하나는 "기반 규정 + 특칙 0~1개"의 스택이라는 점을 폴더가 그대로 보여 준다.

```text
00-practice-standards-start/  입구 — 짧게 유지. 작업 유형 → workflows
workflows/                    작업 절차 (어떻게 일하는가)
foundations/  foundation-*    기반: 공통 [100]~[500]
assets/       asset-*         기반: 물건 [600] — real-estate / industrial / movables / intangibles / income-and-loss
overlays/     overlay-*       특칙: 목적별 [700] (purpose/) · 보상평가 [800] (compensation/)
```

- **특칙은 보통 하나지만 배타적이지 않다**: 두 가지를 구분한다.
  - 우선순위(보상 > 목적 > 물건 > 공통)
  - 호출 관계: 특칙 원문이 다른 절로 보내는 것. 예: 도시정비 수용등 [730-3.5] → [800], 사용 토지 [820-5.2.1-2] → [810-5.6]
  호출된 절은 읽을 목록에 넣지만 우선순위는 스택 순서를 따른다.
- **workflows 와 내용 스킬 분리**: 절차(무엇을 어떤 순서로)와 내용(원문 요약)을 섞지 않는다. 내용 스킬은 원문 절과 1:1 이라 개정 때 기계적으로 갱신된다. 절차 스킬은 사람이 설계한다.
- **overlays 로 묶은 이유**: 목적별 절과 보상평가 절은 모두 "이 절이 우선하고 나머지는 [100]~[600]을 적용·준용한다"는 같은 구조다. 우선순위 결정에서 같은 자리(특칙)에 놓인다. 일반 평가와 보상평가의 구분은 하위 폴더(purpose/·compensation/)와 결정 사실 F1 로 유지한다.
- **assets 하위 폴더**: 물건 스킬 27개를 한 메뉴에 두면 길다. 실무기준 610~670 장 구분은 대체로 따르되, 의제부동산(640)과 동산(670-1)은 movables 로 모았다. 임대료·권리금·가치하락분(670-2~4)은 물건이라기보다 산정 대상이 되는 가치이므로 income-and-loss 로 모았다.
- **이름**: `<층>-<주제>`. 폴더 이름과 같고 저장소에서 유일하다. 스킬을 평평하게 설치해도 층을 알 수 있다. 입구는 `00-` 으로 시작해 메뉴 맨 위에 온다.
- **입구를 짧게**: 상주시킨다면 입구만 상주하므로, 입구에는 유형 판별과 지도만 둔다.

## 5. 검증

- `tools/validate.py`:
  - 이름·폴더 일치, leaf rule, 링크를 검사한다.
  - 입구·workflows 가 모든 내용 스킬을 언급하는지 검사한다.
  - `split_standard.py --check`(원문 배정, 생성물 최신)를 함께 실행한다.
- [workflows/workflow-appraisal/cases.md](../appraisal-practice-standards/workflows/workflow-appraisal/cases.md): 라우팅 사례와 기대 결과. 절차를 고치면 이 사례로 확인한다.
- 독립 에이전트 사용성 검토: 아래 6절.

## 6. 독립 에이전트 검토

### 방법

설계 맥락이 없는 에이전트 3개에 같은 지시를 줬다. 모델은 gpt-6.1-sol, gpt-6.1-terra, Claude(general-purpose)다.
- 각 에이전트는 저장소 루트에서 시작해 사례집(cases.md)에 없던 과제 5개를 읽기 전용으로 풀었다.
  - 담보 복합부동산
  - 미지급용지·송전선로 보상
  - 공사중단 건축물 질의
  - 재무보고 기계기구류 평가서 검토
  - 어선+어업권 경매
- 연 파일 순서, 망설인 지점, 답(조항 인용)을 기록하게 했다.
- 그다음에야 이 문서를 읽고 설계를 비평하게 했다.

### 결과

- 세 에이전트 모두 다섯 과제에서 기대한 특칙·물건 스킬과 핵심 조항에 도달했다. 과제당 4~12개 파일, 100~600줄을 읽었다.
- 내용 스킬 요약에서 원문과 상반되는 오류는 보고되지 않았다.
- **유지하자는 의견(3/3)**:
  - 작업 유형 입구와 짧은 입구 스킬
  - 결정 사실 → 우선순위 스택, 적용/준용 구분
  - SKILL.md/source.md 분리와 조항 인용 형식
  - 결정적 색인·grep (임베딩 검색 반대)
  - 생성 블록과 validate.py
- **폴더 구조**:
  - 2/3 은 역할 층 + asset 계열 폴더가 원문 장별·평면·물건/목적 단독 구조보다 낫다고 평가했다.
  - 1/3 은 이름이 유일하니 평면 asset 목록도 찾기는 같다고 봤다.
  - 선박이 movables 에 있는 것이 원문의 "의제부동산"과 어긋난다는 지적이 2건 있었다.
  - 임대료·권리금의 income-and-loss 가 직관적이지 않다는 지적이 1건 있었다.

### 반영하지 않은 것

- **평면 asset 목록**: 다수 의견과 메뉴 길이를 고려해 계열 폴더를 유지했다.
- **movables 이름**: 선박 등이 법률상 의제부동산이라는 점은 README·입구에 "[640] 의제부동산 + [670-1] 동산"으로 명시하는 데 그쳤다.
- **"함께 읽을 스킬"의 필수/조건부/관련 등급화**: 41개 스킬 전체 개정이 필요하므로 후속 과제로 남긴다. 그 대신 두 가지를 넣었다.
  - 워크플로 규칙
  - 모든 내용 스킬 머리의 자동 생성 문구: "함께 읽을 스킬은 후보 목록이다. 결정 사실에 해당하는 것만 읽는다." 내용 스킬을 바로 연 에이전트도 이 문구를 보게 된다.

### 후속 검토

수정 후 같은 검토자에게 다시 확인받았다. Claude 검토자의 판정은 다음과 같다.
- 5개 권고 중 4개는 충분히 반영됐고, 1개(쌍 링크)는 부분 반영이다.
- 새 규칙에서 원문과 어긋나는 점은 없다. 확인한 조항: [400-4-②·③], [650-2.3.2-①], [650-1.3-①], [730-3.5], [820-5.2.1-2], 별칭 대상 조항 약 15개.
- "독립 에이전트가 반복 사용하기에 적합하다"고 판정했다.
- 남은 가장 큰 문제로 위 등급화를 지적했다. 이에 따라 자동 생성 문구를 추가했다.

Sol 검토자의 재검토 판정도 "적합"이다. 남은 지적은 두 가지였다.
- 특칙 호출 그래프와 법적 우선순위를 같은 "스택"이라는 말로 섞어 썼다.
- README 에 "0~1개" 문구가 남아 있었다.

workflow-appraisal 2단계에서 우선순위와 호출 관계를 분리해 정리하고, README·입구 문구를 고쳤다.
[820-5.2.1] 설명에는 "구분지상권 설정 또는 임대차계약 등에 따른 사실상 영구 사용"과 한시적 사용을 원문대로 구분해 넣었다.
